The Events endpoints give you access to LatePoint's events module: events and their dates, event categories, registrations, and the LatePoint Pro e-tickets and waiting list.

All Events endpoints live under `/wp-json/latepoint-api/v1/events` and use the same [authentication](/authentication) and response format as the rest of the API.

## Requirements

- **LatePoint 5.7 or newer.** On older versions every Events endpoint returns `503 feature_not_available`.
- **"Enable Events" setting.** Write operations (create, update, delete, cancel, check-in and waiting list actions) return `503 feature_disabled` when Events is turned off in LatePoint settings. Read operations keep working.
- **LatePoint Pro Features** for ticket types, e-tickets and the waiting list (see [Pro features](#pro-features)).

## Dates and times

Event dates and times follow one rule:

- **Request values** and the response fields `start`, `end`, `registration_start` and `registration_end` are in the **site timezone** (the timezone configured in WordPress), formatted as `YYYY-MM-DD HH:MM`. Seconds are optional, and a date alone (`YYYY-MM-DD`) means `00:00`.
- Fields ending in **`_utc`** (`start_utc`, `end_utc`) are in **UTC**.
- Every event includes a `timezone` field with the site timezone name, for example `America/Montevideo`.

```json
{
  "start": "2026-12-05 09:00:00",
  "start_utc": "2026-12-05 12:00:00",
  "timezone": "America/Montevideo"
}
```

An event can have several dates (for example a two-day retreat). The event's overall `start` and `end` are calculated from its dates: `start` is the earliest date start and `end` is the latest date end. They are recalculated every time a date is added, changed or removed.

<Note>
  The `created_after` and `created_before` filters of [List Registrations](/api-reference/events/registrations-list) are an exception: they compare against the stored `created_at` value and are expressed in UTC (`YYYY-MM-DD HH:MM:SS`).
</Note>

## Registrations

Registrations are created by customers through LatePoint's booking form and checkout, not through the API. The API lets you read registrations and cancel them.

Cancelling a registration works like the **Cancel** action in the LatePoint admin. It does **not** cancel or refund the order the registration belongs to. Manage the order separately with the [Orders](/api-reference/orders/get) and [Payments](/api-reference/payments/list) endpoints.

Order items for events have `variant: "event_registration"`. [Get Order](/api-reference/orders/get) includes the related registration in each of those items.

## Pro features

Some event features come from **LatePoint Pro Features** and must also be enabled in LatePoint settings:

| Feature | Where it appears in the API |
|---------|------------------------------|
| Ticket types | `use_ticket_types` and `ticket_types` fields on events; `ticket_types` on registrations |
| E-Tickets | `/events/tickets` endpoints; `tickets` on registration details |
| Waiting list | `/events/waiting-list` endpoints; `waiting_list` settings on events |

Pro fields are only included in event responses when the feature is enabled, and Pro request fields are ignored when it is not. Pro endpoints return one of these errors when the feature is unavailable:

```json
{
  "code": "feature_not_available",
  "message": "E-Tickets requires LatePoint Pro Features",
  "data": {
    "status": 503
  }
}
```

```json
{
  "code": "feature_disabled",
  "message": "Waiting List is disabled in LatePoint settings",
  "data": {
    "status": 503
  }
}
```

## Availability Errors

| Status | Code | When |
|--------|------|------|
| `503` | `feature_not_available` | LatePoint is older than 5.7 (`Events require LatePoint 5.7 or newer`), or a Pro endpoint is called without LatePoint Pro Features |
| `503` | `feature_disabled` | A write operation is called while Events is disabled, or a Pro endpoint is called while that Pro feature is disabled |
